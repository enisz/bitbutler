# ESLint v9+ Flat Config Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace `.eslintrc.json` + `.eslintignore` with ESLint flat config (`eslint.config.mjs`), bump ESLint 8.57.1 -> 10.9.0 and `@angular-eslint/*` 21.4.0 -> 22.1.0 (via the `angular-eslint`/`typescript-eslint` umbrella packages), and get `npm run lint` back to zero warnings.

**Architecture:** This is a tooling-config migration, not an application code change. One new root-level `eslint.config.mjs` replaces four `overrides` blocks from `.eslintrc.json` on a strict parity basis (same rules linted on the same files as today, plus `packages/shared/src` which was missing from the actual `lint` script despite having a dead override for it). `package.json` devDependencies swap five granular `@angular-eslint/*`/`@typescript-eslint/*` packages for two umbrella packages plus the ESLint major bump. A final pass fixes whatever the newer plugin versions (and the newly-linted `shared` package) surface, verified by `npm run lint`, `npm test`, and both build commands.

**Tech Stack:** ESLint 10, `angular-eslint` 22.1.0 (umbrella), `typescript-eslint` 8.67.0 (umbrella), `eslint-plugin-prettier` 5.5.5 (unchanged, already flat-config-ready via its `/recommended` export).

**Spec:** `docs/superpowers/specs/2026-08-22-eslint-v9-flat-config-migration-design.md`

## Global Constraints

- `npm run lint` must stay at zero warnings (`--max-warnings=0`) - non-negotiable exit criterion.
- No dependency bump outside `eslint`, `angular-eslint`, `typescript-eslint` (removing the five now-redundant granular packages doesn't count as a "bump" - see spec).
- Do not add `eslint.configs.recommended` or `tseslint.configs.recommended` - tracked separately as issue #287.
- Do not add `@angular-eslint/builder` or an `ng lint` architect target.
- Do not add the `angular.processInlineTemplates` processor.
- Target versions: `eslint@^10.9.0`, `angular-eslint@^22.1.0`, `typescript-eslint@^8.67.0`.
- Commit format: `#272: <short description>` (this repo's convention).
- Before opening the PR, remove the `docs/superpowers/specs` and `docs/superpowers/plans` files added for this issue in their own commit (`#272: removed spec and plan`) - they must not be merged to `main`.

## Task 3: Fix lint violations surfaced by the migration

**Files:**

- Modify: whichever files `npm run lint` flags (expected candidates per the spec: `packages/app/src/**` components missing `ChangeDetectionStrategy.OnPush` for the new `@angular-eslint/prefer-on-push-component-change-detection` rule; `packages/shared/src/**/*.ts`, linted for the first time)

**Interfaces:**

- Consumes: the `eslint.config.mjs` from Task 2.
- Produces: `npm run lint` exits 0 with zero warnings (the plan's exit criterion).

- [ ] **Step 1: Run lint and read the full output**

  Run: `npm run lint`

  Read every reported error/warning - file, line, rule ID, message.

- [ ] **Step 2: Fix each violation at its source**

  For each reported rule violation:
  - If it's `@angular-eslint/prefer-on-push-component-change-detection` on a component that has no reason to avoid `OnPush` (i.e. it doesn't rely on default change detection for something `OnPush` would break), add `changeDetection: ChangeDetectionStrategy.OnPush` to that `@Component` decorator and import `ChangeDetectionStrategy` from `@angular/core` if not already imported.
  - If switching a specific component to `OnPush` would change its behavior (relies on default-strategy detection picking up mutations `OnPush` wouldn't catch), do not force the switch - instead disable the rule for that one component with `// eslint-disable-next-line @angular-eslint/prefer-on-push-component-change-detection -- <one-line reason>` directly above the `@Component` decorator.
  - For any other rule violation (e.g. something newly caught in `packages/shared/src`), fix the underlying code. Only fall back to a scoped `eslint-disable` comment with a stated reason if the flagged code is intentional and correct as-is.
  - Never blanket-disable a rule repo-wide to silence it - each disable must be scoped to one line/block with a reason.

- [ ] **Step 3: Re-run lint until clean**

  Run: `npm run lint`

  Expected: exits 0, no output (matches `--max-warnings=0`). Repeat Steps 1-3 until this holds.

- [ ] **Step 4: Commit**

  Commit the fixes. If the changes are all one cohesive fix-up, a single commit is fine:

  ```bash
  git add -A
  git commit -m "$(cat <<'EOF'
  #272: fix lint violations surfaced by the v22 angular-eslint rule set

  EOF
  )"
  ```

  If the violations fall into clearly distinct groups (e.g. one commit for `OnPush` component fixes, a separate one for `packages/shared` fixes), split them - use your judgment based on what actually got fixed in Step 2.
